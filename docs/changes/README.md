# 패치노트 조각 관리

기능 개발과 오류 수정 PR은 사용자·운영자가 이해할 수 있는 패치노트 조각을
`docs/changes/unreleased/`에 하나씩 추가합니다. 개발 PR마다 공식 버전을
변경하지 않고, 릴리즈 PR에서 조각을 모아 공식 변경 이력과 업데이트 공지를
작성합니다.

## 목적

- 코드 변경과 사용자 안내를 같은 PR에서 함께 검토합니다.
- 여러 PR이 `docs/CHANGELOG.md`의 같은 위치를 수정해서 생기는 충돌을 줄입니다.
- 커밋 메시지보다 읽기 쉬운 게임 업데이트 공지 형태의 릴리즈 노트를 만듭니다.
- DB, 환경변수, 컨테이너, 기존 데이터에 미치는 영향을 릴리즈 전에 확인합니다.

## 파일 이름

다음 형식을 사용합니다.

```text
<분류>-<짧은-설명>.md
```

예시:

```text
feature-eo-preview.md
improvement-processing-progress.md
fix-upload-retry.md
performance-map-rendering.md
security-project-assets.md
operations-container-startup.md
breaking-storage-layout.md
```

한 PR에서 서로 독립적인 변경이 여러 개라면 파일을 나눕니다. 같은 사용자
흐름을 완성하는 변경은 하나의 조각으로 작성할 수 있습니다.

## 분류

| 분류 | 용도 |
|---|---|
| 신규 기능 | 사용자가 새로 사용할 수 있는 기능 |
| 기능 개선 | 기존 기능의 동작이나 사용성 개선 |
| 버그 수정 | 의도와 다르게 동작하던 문제 수정 |
| 성능 개선 | 처리 시간, 메모리, 렌더링, 업로드 성능 개선 |
| 운영·배포 | 설치, 환경변수, 컨테이너, 모니터링 변경 |
| 보안 | 인증, 권한, 데이터 접근 정책 변경 |
| 호환성 변경 | API, DB, 설정, 저장소 구조 등 기존 호환성이 깨지는 변경 |

## 작성 절차

1. `docs/changes/TEMPLATE.md`를 복사해 `unreleased/` 아래에 저장합니다.
2. 대상 버전은 현재 코드 버전이 아니라 변경이 들어갈 예정인 버전을 씁니다.
3. 구현 설명보다 변경 전후의 사용자 경험을 먼저 적습니다.
4. DB 마이그레이션, 설정, 재빌드, 데이터 영향이 없더라도 `없음`이라고 명시합니다.
5. PR 본문에 조각 파일 경로를 연결합니다.

사용자·운영자에게 보이는 변화가 없는 테스트, 내부 리팩터링, 오탈자 수정은
조각을 생략할 수 있습니다. 이 경우 PR 본문에 생략 사유를 적습니다.

## 버전과 릴리즈

일반 개발 PR에서는 루트 `VERSION`과 배포 버전을 변경하지 않습니다. 릴리즈
PR에서 다음 작업을 한 번에 수행합니다.

1. 포함할 `unreleased/` 조각을 검토합니다.
2. 조각을 `docs/changes/<버전>/`으로 이동해 보관합니다.
3. `docs/PATCH_NOTES_TEMPLATE.md`를 사용해 최종 업데이트 공지를 작성합니다.
4. `docs/CHANGELOG.md` 최상단에 공식 릴리즈 항목을 추가합니다.
5. `VERSION`과 연동된 모든 버전 표기를 함께 변경합니다.
6. 버전 검사, 테스트, 패키징, 태그 생성을 수행합니다.

현재 정식 기준은 `v2.0.1`입니다. 이후 호환 기능 추가 조각은 `v2.1.0`을
대상으로 기록하고, 운영 검증판이 필요하면 릴리즈 PR에서
`v2.1.0-rc.1`로 확정합니다.

현재 확정된 운영 검증 후보는 `v2.1.0-rc.5`이며 포함 조각은
`docs/changes/v2.1.0-rc.5/`에 보관합니다.

## 작성 원칙

- 내부 클래스명이나 커밋 설명보다 사용자가 얻는 결과를 먼저 씁니다.
- `개선했습니다`로 끝내지 말고 무엇이 어떻게 달라지는지 적습니다.
- 과장된 표현이나 검증하지 않은 성능 수치를 사용하지 않습니다.
- 알려진 제한과 필요한 운영 작업을 숨기지 않습니다.
- 한 항목에 기능 설명과 운영 절차가 섞이면 별도 문단으로 나눕니다.
